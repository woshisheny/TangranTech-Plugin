## 三阶段变身崩在 MAX_HEALTH 上限（Health value (2000.0) must be between 0 and 1024.0）

**根因**：`BossPhaseThreeFour.spawnTangranZombie` 按原脚本口径 `mobHp = 100 × 血条剩余`
（双子全灭剩 20 → 2000）直接 `attr.setBaseValue(2000)`。原版 `AttributeInstance.setBaseValue`
对基础值有 [0, 1024] 硬校验 → 抛 `IllegalArgumentException`；写属性那段有 try 吞掉，
但紧随其后的 **`ent.setHealth(2000)` 没有 try** → 异常冒到方法外层 catch，
打「糖然变身失败」并**中断**：`duelMob` 未记录、`startDuelTask` 未启动 →
僵尸站在场上不动、三阶段整段死掉（不是「只是血少了」，是流程断了）。

RSC 原脚本同款写法（BOSS战.js 10654-10661）两处都 try 了，后果是僵尸保持原版 20 血、
而 `d.maxHp` 仍为 2000 → 血条折算 `ceil(hp/2000*20)` 恒为 1，实质「一刀通关」。

**修复**（不引入新机制，只处理上限）：
- 新增常量 `VANILLA_MAX_HEALTH_CAP = 1024`、`DUEL_HP_PER_BAR = 100`；
- 新增 `applyDuelHealth(Zombie, wanted)`：`min(1024, wanted)` → `setBaseValue` → **回读 `attr.getValue()`**
  当实际上限 → 再用 `getMaxHealth()` 兜底 → `setHealth(实际上限)`，全程 try，返回**实际生效上限**；
- `duelMaxHp` 存返回值（不是 wanted），血条折算 `hp / duelMaxHp * duelBarHp` 因此仍线性
  （满血 1024 → 20，半血 → 10，死 → 0）；
- 日志加「（原口径 2000 超原版上限 1024，已截断）」；同步改三处口径注释
  （类 javadoc 血量口径、`BossState.duelMaxHp`、`BossTwin.DEFEAT_HP_DROP`）。

**代价**：决斗体上限 1024 而非原意 2000 → 三阶段时长约为设计的一半。要恢复原节奏只有两条路
（本次未做，未获需求）：① 对决斗体收到的伤害乘 1024/2000（等效 2000 血）；② 用吸收/自管 HP 池。
其余 BOSS 血量（Katarina 600 / 双子 300 / zqx125 1024）均在限内，无需处理。
