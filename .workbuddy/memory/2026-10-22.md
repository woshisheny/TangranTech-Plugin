### 追加 3：参考外部解析 → 发现并修复「普通箭打末影人 0 伤害」

用户提供了一份机制解析，核心结论：
- `EnderMan.hurt()` 中，若 `DamageSource` 带 `IS_PROJECTILE` 标签（箭/三叉戟/雪球），末影人会随机瞬移并
  `return false` → **免疫伤害**；`EntityDamageByEntityEvent` 因此**也不会触发**。
- 正解：命中末影人时手动 `enderman.damage(amount, player)` —— **以玩家为伤害源**，绕开投射物分支。

据此核对 Pofabow：
- `trueDamage()` 走 `setHealth` → 已天然绕过免疫（特殊箭无问题）。
- **`endermanPreHit` 的普通箭分支是 `target.damage(dmg, arrow)` —— 伤害源是箭，同样带 IS_PROJECTILE，
  照样被免疫，而箭随后被 `remove()` ⇒ 普通模式射末影人 = 白射一箭（真 bug）。**
- 修复：普通箭分支改为 `target.damage(dmg, shooter)`（玩家为源），保留无源兜底。已在 javadoc 记档机制原文。

顺带确认架构与解析建议一致：以 `ProjectileHitEvent`（`onHit`）为主路径、tick 扫描作兜底；
上一轮把「每刻盒查询」换成「发射锁目标 + 每刻 O(1) 距离比较」正是其兜底环节的等价优化。

### 追加 4：回归修复（用户实测反馈后）

### 追加 5：造物机器运行期报错修复（Slimefun error-reports 04-13 / 04-14）

两份 .err 是同一个根因，且都指向**造物匣系列**（`TR_ZWXCREATOR`、`TR_ZWXZSG`，
机器定义在 `content/mat_generators.yml`，共 130 条）：

```
java.lang.IllegalArgumentException: The Ingredients array cannot be empty or null
  at ...CraftingOperation.<init>(CraftingOperation.java:28)
  at com.tangran.tangrantech.machines.TTRecipeMachine.tick(TTRecipeMachine.java:242)
```

**根因链**（是当年 P0「造物匣 130 台永不工作」修复的**后续**）：
1. 造物匣**无输入槽**；`MaterialGeneratorsLoader` 用 `Recipes.readOutputs(s, tickRate)` 构造配方
   → `new TTRecipe(ticks, new ItemStack[0], outs, ...)`，**input 恒为空数组**。
2. 早先 P0 修了 `findMatch` 的「空输入早退」（加了 `slotCount > 0` 守卫），
   于是造物匣**能匹配到配方了**；
3. 但 `TTRecipeMachine.tick()` 第 242 行**无条件** `new CraftingOperation(next)`，
   而 Slimefun 的 CraftingOperation 构造时 `Validate.notEmpty(recipe.getInput())`
   → 空配料直接抛异常，每 tick 炸一次。

**修复**：`tick()` 里在创建 operation 前判 `tr.getInput().length == 0`，
命中则走新增的 `produceWithoutInput(b, inv, r)` —— 不进 operation，
按配方自身周期 `Math.max(1, r.getTicks())`（即 yml 的 tickRate）节流：
取电成功才记录 `lastGen[location] = Bukkit.getCurrentTick()` 并产出。
新增字段 `private final Map<Location, Long> lastGen`（ConcurrentHashMap）。

**关联认知**
- 机器 ID → yml 的映射：报错里的 `TR_ZWX*` / `TR_ZWXCREATOR` 系列定义在
  `mat_generators.yml`（130 条），菜单在 `menus.yml` 的 `Tr_zwx*` 同名键。
- Slimefun 的 `CraftingOperation` **不接受空配料**，凡是「无输入槽」的机器
  （物质生成器 / 造物匣）都必须绕开它另开产出路径。
- 启动期那 50+ 条「进度槽 22 与输入/输出槽重叠」是 `menus.yml` 这些菜单
  **缺 progressbar 配置**导致（代码已安全降级为「禁用进度占位」，非故障）。
  用户指认「造物机器的进度展示槽位可放 41」，批量补配置留待确认后处理。

**我们这边「配方丢失」的真正根因**（和上面是两个问题，别混）：

⇒ 指南里**一条配方都不显示**。

PDC 键用我们自己的 `tangrantech:recipe_index`（`NamespacedKey.fromString`）。
顺带删掉 `TTMaterialGenerator.getDisplayRecipes()` 那个仅转发 super 的死代码覆盖。

### 追加 7：配方按钮点击链路（对齐 RSC MachineMenuPreviewGroup + RecipeViewListener）

用户实测确认按钮已出现但点击无反应（上轮只做了展示层）。已按 RSC 完整复刻三层机制：

**RSC 三层机制**（源 `bulit_in/recipes/` + `listeners/RecipeViewListener.java` + `bulit_in/MachineMenuPreviewGroup.java`）：
1. **展示层** `RecipesHolder.getDisplayRecipes()`：每配方产 [输入展示, 输出展示]；
   单物品直接显示，多物品显示绿色玻璃板按钮（PDC `rsc_recipe_index`=下标）。
2. **点击层** `RecipeViewListener`（LOW 优先级）：点击物品带索引 PDC →
   **`e.getInventory().getItem(16)`**（`GUIDE_ITEM_OUTPUT_INDEX=16`，Slimefun 指南物品页固定在 16 号槽放机器本体）
   → `SlimefunItem.getByItem` 定位机器 → `Recipe.openGUI(p, ac, idx)`。
3. **详情层** `MachineMenuPreviewGroup extends FlexItemGroup`：
   - `profile.getGuideHistory().add(this, 0)` —— **把预览页塞进指南历史栈**（返回键能回机器页的关键）；
   - `presetMenu()` 按机器真实菜单布局铺背景（RSC 用 CustomMenu，我们用 MenuDef）；
   - `rp.formatGUI()` 把输入铺输入槽、输出铺输出槽；
   - 进度槽放耗时；`tryAddBackButton()` 在空白玻璃板背景上塞返回按钮
     （isBackground 判定：`_STAINED_GLASS_PANE` 结尾 + 名字空白 + lore 空白）；
     history.size()==1 或 Shift → openMainMenu，否则 goBack；
   - 剩余空槽全部挂 empty handler（预览界面什么都不能拿）。

**我们的实现**（新文件 `machines/RecipePreview.java`，约 250 行）：
- `RecipePreview.registerOnce()`：幂等注册点击监听，由 TTRecipeMachine 构造器调用；
- 点击监听：PDC 索引（`tangrantech:recipe_index`）+ 槽 16 机器物品 → instanceof TTRecipeMachine → cancel + open；
- `Group extends FlexItemGroup`：isVisible 恒 false（只作历史条目）；open 里
  guideHistory.add → buildMenu（menu.items 背景 + inSlot 绑定优先的输入铺放 + 输出概率 lore +
  进度槽耗时 + 空白玻璃板塞返回按钮 + 空槽补背景）→ inv.open(p)；
- 返回按钮：`SlimefunGuide.openMainMenu(profile, mode, history.getMainMenuPage())` /
  `history.goBack(Slimefun.getRegistry().getSlimefunGuide(mode))`。

**踩过的坑**：Slimefun `openMainMenu` 签名是三参 `(PlayerProfile, SlimefunGuideMode, int)`，不是两参。
